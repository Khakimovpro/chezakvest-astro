# Переключение доменов на московский сервер

Переезд разделён на два независимых этапа. Сначала включается тестовый `chezakvest.com`; боевой
`чезаквест.рф` (`xn--80aehcht5ci1b.xn--p1ai`) переводится только по отдельному решению владельца.
Скрипт не выбирает этап автоматически: во всех командах обязателен `--stage test` или
`--stage production`.

Перед любым изменением сохраните скриншот или экспорт DNS-зоны. Меняйте только перечисленные ниже
A-записи веб-хостов. MX, TXT, SPF, DKIM, DMARC и остальные почтовые записи не меняйте. Если у
затрагиваемого веб-имени есть AAAA-запись, удалите именно её: на московском сервере IPv6 не
настроен, а Let's Encrypt может выбрать старый IPv6-адрес.

## Этап 1 — тестовый домен chezakvest.com

DNS-зону обслуживают `ns1.reg.ru` и `ns2.reg.ru`. В панели REG.RU откройте зону
`chezakvest.com` и установите две записи:

| Имя записи | Тип | Значение | TTL |
| --- | --- | --- | --- |
| `@` | `A` | `82.146.60.212` | `300` секунд |
| `www` | `A` | `82.146.60.212` | `300` секунд |

Не заменяйте `www` на CNAME: скрипт ожидает единственную A-запись на обоих именах и выпускает
сертификат Let's Encrypt сразу для `chezakvest.com` и `www.chezakvest.com`.

До изменения обе записи указывали на `95.163.244.138`, а авторитетные NS REG.RU отдавали TTL
86400 секунд. Поэтому старый адрес может оставаться в кэше резолверов до 24 часов, даже если для
новой записи уже выбран TTL 300 секунд. Не запускайте реальное переключение, пока публичные
проверки не покажут только новый IPv4 и пустой IPv6:

```bash
dig @1.1.1.1 +short A chezakvest.com
dig @1.1.1.1 +short A www.chezakvest.com
dig @1.1.1.1 +short AAAA chezakvest.com
dig @1.1.1.1 +short AAAA www.chezakvest.com
dig @8.8.8.8 +short A chezakvest.com
dig @8.8.8.8 +short A www.chezakvest.com
```

Оба A-запроса должны вернуть только `82.146.60.212`, оба AAAA-запроса — ничего. Затем из корня
репозитория сначала посмотрите план, после чего запустите переключение:

```bash
deploy/enable-domain.sh --stage test --dry-run
deploy/enable-domain.sh --stage test
```

Успех — сообщение `Переключение домена завершено успешно`, HTTPS-главная отвечает 200,
`www` постоянно перенаправляет на домен без `www`, сертификат содержит оба имени, а проверки
индексации проходят:

```bash
curl -sS -I https://chezakvest.com/
curl -sS -I https://www.chezakvest.com/
curl -sS https://chezakvest.com/robots.txt
curl -sS -I https://chezakvest.com/sitemap.xml
curl -sS https://chezakvest.com/ | grep -o -m1 '<link rel="canonical"[^>]*>'
```

Ожидается `X-Robots-Tag: noindex, nofollow`, отсутствие `Strict-Transport-Security`,
`Disallow: /` без `Allow` и `Sitemap` в `robots.txt`, статус 404 у `sitemap.xml` и canonical на
`https://xn--80aehcht5ci1b.xn--p1ai/`. У `www` ожидается 301 на тот же путь
`https://chezakvest.com/...`.

### Почему тестовый домен закрыт от индексации

Сборка остаётся боевой: её HTML, исходный `robots.txt` и `sitemap.xml` содержат боевой домен.
Менять эти файлы ради временного хоста нельзя — иначе пострадает будущий боевой этап. Поэтому
тестовый nginx поверх сборки отдаёт отдельный `robots.txt` с `Disallow: /` и отвечает 404 на
`sitemap.xml`. Заголовок `X-Robots-Tag: noindex, nofollow` остаётся на страницах и ассетах, а HSTS
не отправляется совсем: тестовый хост временный, и браузеры не должны запоминать принудительный
HTTPS для него.

Canonical в HTML не создаёт дубль: он указывает не на тестовый хост, а на существующий боевой
URL. Если робот всё же запросит страницу напрямую, canonical просит объединить сигналы с боевой
страницей, а `X-Robots-Tag` запрещает индексировать тестовый ответ. Закрытый robots и отсутствующий
sitemap дополнительно не дают тестовому хосту самому приглашать обход.

### Как вернуть тестовый домен назад

1. В REG.RU восстановите обе прежние A-записи из сохранённого экспорта. На 4 сентября 2026 года
   это были `@ → 95.163.244.138` и `www → 95.163.244.138`.
2. Дождитесь, пока публичные резолверы снова показывают прежний адрес.
3. Верните nginx московского сервера в состояние до тестового этапа:

```bash
deploy/enable-domain.sh --stage test --rollback
```

Тестовый этап намеренно не включает HSTS, поэтому браузеры не закрепляются за московским сервером.
Если DNS уже возвращён, но rollback-state отсутствует, домен всё равно обслуживается прежним
хостом; не меняйте сервер вручную и проверьте сообщение сухого запуска
`deploy/enable-domain.sh --stage test --rollback --dry-run`.

## Этап 2 — боевой домен чезаквест.рф

Этот этап не выполняйте без отдельного решения владельца. Зону `чезаквест.рф` обслуживает Beget.
После разрешения замените в Beget A-записи `@` и `www` на `82.146.60.212`; прежний подтверждённый
адрес на 4 сентября 2026 года — `185.215.4.18`. Если отдельно решено переводить `chezakvest.ru`,
в REG.RU замените его `@` и `www` на `82.146.60.212` (прежний адрес — `77.222.61.25`).

Скрипт обязательно ждёт A-запись корня боевого домена. Остальные имена — `www` боевого домена,
`chezakvest.com`, его `www`, `chezakvest.ru` и его `www` — он добавит в сертификат и направит на
боевой canonical только тогда, когда их единственная A-запись уже равна `82.146.60.212` и AAAA
отсутствует.

После распространения DNS выполните:

```bash
deploy/enable-domain.sh --stage production --dry-run
deploy/enable-domain.sh --stage production
```

Боевой этап сначала проверяет HTTPS без HSTS и с временным noindex, затем включает
`Strict-Transport-Security: max-age=31536000`, снимает `X-Robots-Tag` и запускает строгий
`npm run verify:live`. Успех — сообщение скрипта, HTTPS 200 на боевом canonical и 301 всех
подтверждённых альтернатив на тот же путь боевого домена.

Для планового возврата сначала восстановите в Beget и других затронутых панелях точные прежние
A-записи из экспорта. Пока изменение распространяется, оставьте текущий production-конфиг nginx:
он продолжит обслуживать клиентов со старым DNS-кэшем. После того как публичные резолверы покажут
прежние адреса и истечёт прежний TTL, выполните
`deploy/enable-domain.sh --stage production --rollback`. После включения HSTS возвращённый боевой
хост обязан сохранять рабочий HTTPS-сертификат.

Если production-команда сама завершилась ошибкой, она автоматически вернёт предыдущий nginx.
Сразу восстановите прежние DNS-записи. Пока старые кэши ещё ведут на московский IP, часть HTTPS-
запросов может получать сертификат предыдущего тестового этапа; это аварийное окно заканчивается
после распространения возвратных DNS-записей.
