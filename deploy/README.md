# Выкладка сайта на московский сервер

Скрипт запускается только из корня репозитория. Для обычного релиза нужен чистый Git и доступ к
`root@82.146.60.212` ключом `~/.ssh/chezakvest_key` (другой путь можно передать через
`CHEZAKVEST_SSH_KEY`).

## Релиз одной командой

```bash
deploy/deploy.sh
```

Скрипт запускает полный `npm run ci`, повторно проверяет неизменность исходников и использует
финальный проверенный этим гейтом `dist/`. Затем он добавляет `version.json`, передаёт сборку во временный каталог через rsync и
проверяет её контрольными суммами. Только после проверки каталог получает окончательное имя,
а файлы на сервере принадлежат `root:root`. Затем скрипт атомарно переключает
`/var/www/chezakvest/current` и конфигурацию nginx одной удалённой транзакцией, выполняет
HTTP-смоук и оставляет три последних **принятых** релиза. С каждым принятым релизом хранится
закрытый снимок фактически установленной nginx-конфигурации. Скрипт заранее требует свободное место
не меньше размера артефакта плюс 1 ГиБ, очищает оставшиеся после обрыва `.incoming` и
непринятые каталоги, а смоук сверяет и commit, и уникальное имя релиза. Исходники nginx фиксируются
до долгой доставки и передаются из неизменяемой копии. Общий конфиг и legacy-редиректы обновляются
всегда; stage site-конфиг — только пока TLS ещё не включён. После cutover существующий TLS
site-конфиг сохраняется. Только зелёный релиз получает `.deploy-verified`; откат и retention
игнорируют все каталоги без него.

Полезные режимы:

```bash
deploy/deploy.sh --dry-run
deploy/deploy.sh --skip-gate
deploy/deploy.sh --allow-dirty
```

`--dry-run` только показывает план. `--skip-gate` допустим, когда этот же коммит уже прошёл полный
гейт; в этом режиме выполняется отдельная сборка. Грязное дерево блокирует релиз, пока оператор явно не
передаст `--allow-dirty`.

## Откат одной командой

```bash
deploy/deploy.sh --rollback
deploy/deploy.sh --rollback --to 20260904T025221Z-4bd56d0a
```

Без `--to` откат выбирает следующий более старый принятый релиз относительно активного. Каждый
повторный вызов двигается ещё на один шаг назад; когда более старых принятых релизов нет, команда
завершается с понятной ошибкой и ничего не меняет. `--to <release>` выбирает конкретный релиз по
полному имени и разрешает переключение только на существующий принятый релиз.

Скрипт одной удалённой транзакцией возвращает `current`, site/common/redirect-конфиги nginx и
состояние site-ссылок, затем выполняет `nginx -t`, reload и HTTP-смоук. При штатно обработанной
ошибке исходные релиз и nginx-конфигурация восстанавливаются вместе. Если сама компенсация или
связь с сервером нарушены, команда оставляет owner-token и durable recovery-state: следующий
`--rollback` сначала завершит восстановление, а новую операцию нужно вызвать отдельно. План
автоматического или адресного отката можно посмотреть через `--dry-run`, например
`deploy/deploy.sh --rollback --to <release> --dry-run`.

## Размещение на сервере

- релизы: `/var/www/chezakvest/releases/<UTC-время>-<короткий-коммит>`;
- активный релиз: `/var/www/chezakvest/current`;
- nginx-снимки релизов: `/var/lib/chezakvest/release-configs/<release>/`;
- незавершённый ручной откат: `/var/lib/chezakvest/manual-rollbacks/<operation-token>/`;
- конфигурация nginx: `/etc/nginx/sites-available/chezakvest.conf`;
- общий nginx-конфиг: `/etc/nginx/snippets/chezakvest-common.conf`;
- legacy-редиректы: `/etc/nginx/snippets/chezakvest-legacy-redirects.conf`;
- ACME webroot: `/var/www/acme/.well-known/acme-challenge/`;
- логи: `/var/log/nginx/chezakvest.access.log` и `/var/log/nginx/chezakvest.error.log`.

Перед заменой существующих site/common/redirect-файлов nginx скрипт атомарно сохраняет и побайтово
сверяет копии с суффиксом `.bak-<UTC-время>`. Для каждого файла остаются десять последних копий;
копии, на которые ссылаются действующие точки ручного или автоматического отката, не удаляются.
Снимок релиза содержит фактические site/common/redirect-файлы и состояние site-ссылок, доступен
только root и удаляется той же retention-операцией, что и соответствующий каталог релиза. Перед
активацией следующего релиза снимок активного релиза сверяется с live-конфигурацией и обновляется,
поэтому отдельный test/production cutover не оставляет у него устаревший stage-снимок.
Стандартный `/etc/nginx/sites-enabled/default` отключается, но исходный файл
`/etc/nginx/sites-available/default` остаётся на месте. Выкладка, cutover и полная приёмка используют
общий локальный lock и удерживаемый через SSH серверный lock, поэтому параллельные операции даже с
разных рабочих машин останавливаются до изменения общего состояния.

Серверный lock хранит persistent owner-token в `/var/lib/chezakvest/operation-owner` до штатного
`RELEASE`, а короткие удалённые мутации дополнительно сериализованы отдельным mutation-lock.
При потере SSH тот же процесс может
перехватить lock только со своим token и завершить откат. После жёсткого завершения обычные
выкладка, cutover и приёмка fail-closed сообщат о незавершённой операции; штатный `--rollback`
явно забирает такой token под свободными lock, архивирует его в единственный `.abandoned` и
выполняет восстановление. Обычная активация и ручной откат имеют отдельные durable
prepared/committed markers; ручной marker хранит точный снимок состояния до отката. Token и markers
переживают reboot, а повторное
прерывание recovery сохраняет исходный transaction token. Owner-файлы вручную не удаляют.

## Домены включаются в два этапа

`deploy/enable-domain.sh` не угадывает назначение домена: этап обязательно задаётся явно.

```bash
deploy/enable-domain.sh --stage test --dry-run
deploy/enable-domain.sh --stage production --dry-run
```

Этап `test` делает `chezakvest.com` каноническим только на уровне nginx тестового стенда,
перенаправляет `www.chezakvest.com` на него и выпускает сертификат на оба имени. На всём тестовом
этапе остаётся `X-Robots-Tag: noindex, nofollow`, HSTS не включается, `robots.txt` запрещает обход,
а `sitemap.xml` возвращает 404. Канонические ссылки внутри HTML по-прежнему указывают на боевой
`xn--80aehcht5ci1b.xn--p1ai`.

Этап `production` запускается позже, только после отдельного решения владельца. Он делает
`xn--80aehcht5ci1b.xn--p1ai` каноническим, подхватывает только уже направленные на этот сервер
альтернативные имена, после проверки HTTPS включает HSTS, снимает noindex и запускает строгий
`npm run verify:live`. Перед HSTS точка автоматического отката переносится на уже проверенный TLS
без HSTS, поэтому поздняя ошибка не возвращает сервер к HTTP-only. Отдельная ручная точка
`--rollback` остаётся состоянием до production-cutover. Точные DNS-записи, проверки и откат
описаны в `deploy/DOMEN.md`.

После появления в серверном конфиге `listen 443` или `ssl_certificate` обычный `deploy/deploy.sh`
переходит в TLS-режим: fail-closed проверяет его до и после доставки, не заменяет site-конфиг
stage-шаблоном, но обновляет общий конфиг и редиректы. `deploy/deploy.sh --dry-run` показывает
определённый на сервере режим nginx.
