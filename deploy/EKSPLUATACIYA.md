# Эксплуатация сайта «Чё за Квест»

Сайт — набор готовых статических файлов, которые отдаёт nginx. На сервере нет Node.js и отдельного
приложения: для работы посетителей нужен nginx, исправный активный релиз и свободное место на диске.

## Где что лежит

- сервер: `root@82.146.60.212`;
- все релизы: `/var/www/chezakvest/releases/`;
- активный релиз: ссылка `/var/www/chezakvest/current`;
- конфигурация nginx: `/etc/nginx/sites-available/chezakvest.conf`;
- логи запросов: `/var/log/nginx/chezakvest.access.log`;
- логи ошибок: `/var/log/nginx/chezakvest.error.log`;
- журнал сторожа: системный журнал, метка `chezakvest-watchdog`.

Скрипт выкладки оставляет три последних принятых релиза, удаляет бесхозные `.incoming` и
неактивные каталоги без `.deploy-verified`. Перед доставкой и активацией он требует свободное место
не меньше размера новой сборки плюс 1 ГиБ. Для каждого nginx-файла сохраняются десять последних
резервных копий.

Выкладка, переключение домена и полная приёмка разделяют один серверный lock. Пока одна из этих
операций идёт, вторая с другой рабочей машины завершится до изменения общего состояния.
При потере соединения owner-token не позволяет новому процессу пересечь незавершённый откат.
После жёсткого завершения сначала проверьте dry-run, затем используйте соответствующий штатный
`--rollback`: он забирает оставленный token только под свободными серверными operation- и
mutation-lock. Persistent owner переживает перезагрузку сервера; повторный сбой самого recovery
не затирает исходный transaction token. Не удаляйте
`/var/lib/chezakvest/operation-owner` и `.abandoned` вручную.

## Какая версия работает сейчас

Без входа на сервер:

```bash
curl -fsS http://82.146.60.212/version.json
```

На сервере можно одновременно увидеть каталог активного релиза и его описание:

```bash
readlink -f /var/www/chezakvest/current
cat /var/www/chezakvest/current/version.json
```

Поля `commit`, `builtAt` и `release` показывают исходный коммит, время сборки по UTC и имя релиза.

## Как выкатить новую версию

Запустите из корня репозитория на машине разработки:

```bash
deploy/deploy.sh
```

Нужны чистое рабочее дерево Git и SSH-ключ `~/.ssh/chezakvest_key`. Скрипт сам проверит проект,
соберёт сайт, передаст его на сервер, переключит активный релиз и проверит страницы. Успешное
завершение команды означает, что новая версия прошла живую проверку. Предварительно увидеть план
без сборки и изменений можно так:

```bash
deploy/deploy.sh --dry-run
```

## Как откатиться

Сначала посмотрите план, затем выполните откат:

```bash
deploy/deploy.sh --rollback --dry-run
deploy/deploy.sh --rollback
```

Сухой запуск напечатает строки `Текущий релиз` и `Предыдущий релиз`. Продолжайте только тогда,
когда имя в строке `Предыдущий релиз` — именно та версия, которую нужно включить. Скрипт фактически
выбирает самый новый проверенный релиз, отличный от активного: сразу после обычной выкладки это
действительно предыдущая версия, но повторный вызов после уже сделанного отката может вернуть более
новую версию и тем самым отменить откат.

После проверки имени реальная команда безопасно переключит ссылку `current`, проверит конфигурацию
nginx и страницы. Если её проверка не пройдёт, скрипт вернёт исходное состояние. Если dry-run
показывает не нужную версию, не меняйте `current` вручную: сохранённые каталоги могут быть
непроверенными, а штатный скрипт пока не умеет выбирать конкретный релиз.

## Сторож и ротация логов

Установка или повторное обновление эксплуатационных файлов выполняется из корня репозитория:

```bash
deploy/monitoring/ustanovit.sh
```

Сторож раз в пять минут проверяет главную страницу по внутреннему адресу с явным Host московского
сервера и сверяет `version.json` с именем активного принятого release. Такой probe остаётся HTTP 200
и после доменного cutover, не принимая штатный внешний HTTP→HTTPS 301 за аварию. После трёх неудач
подряд он пытается перечитать nginx без остановки и повторяет попытку на каждой третьей следующей
неудаче, записывая `ACTION`. После успешной проверки счётчик сбрасывается. Внешних сервисов и
ключей у сторожа нет.

Проверить расписание и последние результаты:

```bash
systemctl list-timers chezakvest-watchdog.timer --all
journalctl -t chezakvest-watchdog -n 50 --no-pager
```

Логи nginx вращаются ежедневно, хранятся 14 копий и сжимаются. Сухая проверка настройки:

```bash
logrotate -d /etc/logrotate.conf
```

## Если сайт не открывается

Выполняйте шаги по порядку на сервере. После каждого исправления снова откройте главную и
`version.json`.

1. Убедитесь, что nginx работает:

   ```bash
   systemctl is-active nginx
   systemctl status nginx --no-pager
   ```

   Если он остановлен, посмотрите причину командой `journalctl -u nginx -n 100 --no-pager`, затем
   запустите `systemctl start nginx`. Не перезагружайте nginx при неизвестной ошибке конфигурации.

2. Проверьте конфигурацию:

   ```bash
   nginx -t
   ```

   Только после успешного результата можно выполнить `systemctl reload nginx`. При ошибке сначала
   исправьте названный файл и строку либо восстановите сохранённую рядом копию `.bak-<дата>`.

3. Проверьте активный релиз:

   ```bash
   readlink -f /var/www/chezakvest/current
   test -f /var/www/chezakvest/current/version.json && echo OK
   ls -lah /var/www/chezakvest/releases/
   ```

   Ссылка должна указывать на существующий каталог внутри `releases`, а в нём должен быть
   `version.json`. Если последняя версия повреждена, используйте штатный откат из предыдущего
   раздела.

4. Проверьте место:

   ```bash
   df -h /
   du -sh /var/www/chezakvest/releases /var/log/nginx
   ```

   Не удаляйте активный каталог и предыдущий проверенный релиз. Штатная выкладка сама оставляет
   три последних принятых релиза.

5. Посмотрите свежие ошибки и решения сторожа:

   ```bash
   tail -n 100 /var/log/nginx/chezakvest.error.log
   journalctl -t chezakvest-watchdog -n 50 --no-pager
   ```

6. Проверьте ответ с самого сервера:

   ```bash
   curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1/
   curl -fsS http://127.0.0.1/version.json
   ```

   Если внутренний адрес не отвечает, проблема на сервере. Если он отвечает правильно, а сайт с
   компьютера посетителя нет, переходите к проверке домена и сети.

## Как отделить проблему домена от проблемы сервера

Проверьте сервер напрямую по IP:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' http://82.146.60.212/
```

Затем узнайте, куда сейчас указывает домен:

```bash
dig +short A xn--80aehcht5ci1b.xn--p1ai
dig +short A www.xn--80aehcht5ci1b.xn--p1ai
```

Если IP отвечает, но в DNS нет `82.146.60.212`, nginx и релиз исправны — нужно исправлять
DNS-записи у регистратора и ждать их распространения. Если DNS уже правильный, сравните ответы
через разные сети и проверьте сертификат командой `curl -vI https://xn--80aehcht5ci1b.xn--p1ai/`.
Ошибка имени или срока сертификата относится к настройке домена/TLS; таймаут и по IP, и по домену
указывает на сервер или сеть. Порядок включения домена и возврата DNS описан в `deploy/DOMEN.md`.

Автоматические обновления безопасности установлены, APT раз в семь дней удаляет устаревшие пакеты
из кэша, но автоматическая перезагрузка сервера не включена. Если обновление требует перезагрузки,
файл `/var/run/reboot-required` сообщает об этом; перезагружайте сервер в согласованное время и
после запуска проверьте nginx, сторожа, swap и сайт. В UFW для проекта открыты только 22/tcp,
80/tcp и 443/tcp; профиль ISPmanager не нужен, потому что панель на сервере не установлена.
